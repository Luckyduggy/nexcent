# Nexcent

Курсовий проєкт: сайт (HTML/CSS/JS) + REST API-сервер на **C** з базою **SQLite**.
Увесь сервер — **один файл** [`server/server.c`](server/server.c), без сторонніх бібліотек (окрім SQLite).

## Швидкий старт

```bash
sudo apt install build-essential libsqlite3-dev     # Ubuntu / Debian / WSL
make run                                            # збирає і запускає
```

Відкрийте <http://localhost:3000>. Адмін-акаунт створюється при першому запуску:
`admin@nexcent.example` / `Admin12345!`. **Змініть пароль до першого запуску:**

```bash
ADMIN_EMAIL=me@example.com ADMIN_PASSWORD='мій-пароль' make run
```

Запускати треба **з кореня проєкту** (сервер шукає `database/` і `index.html` у поточній папці).
Потрібен SQLite **3.35+** (Ubuntu 22.04+, Debian 12+, macOS 12+) — перевірка: `sqlite3 --version`.

| Команда      | Що робить                                         |
| ------------ | ------------------------------------------------- |
| `make`       | збирає `build/nexcent`                            |
| `make run`   | збирає і запускає                                 |
| `make test`  | запускає сервер на тимчасовій БД і ганяє 76 перевірок API |
| `make clean` | видаляє `build/`                                  |

Змінні оточення (усі необов'язкові): `PORT` (3000), `DB_PATH` (`database/nexcent.db`),
`ADMIN_EMAIL`, `ADMIN_PASSWORD`.

## Як це працює

```
браузер ──HTTP──► main(): accept() ──► новий потік (pthread) на кожне з'єднання
                                          │
                       /api/...  ◄────────┴────────► усе інше: статичні файли
                          │                          (index.html, pages/, css/, js/, images/)
                 таблиця routes[]
                 (метод + шлях → SQL-запит)
                          │
                       SQLite
```

1. **Потік на з'єднання.** `main()` приймає з'єднання й запускає для кожного окремий потік (`pthread_create`).
   Потік читає запит, відповідає і завершується. Заголовок `Connection: close` — keep-alive немає.
2. **Маршрут = SQL-запит.** У таблиці `routes[]` кожен ендпоінт — це рядок:
   метод, шлях, хто має доступ (`PUBLIC` / `USER` / `ADMIN`), SQL перевірки даних і SQL самої дії.
   SQLite сам читає JSON із тіла запиту (`json_extract(:body, '$.email')`) і сам збирає JSON-відповідь
   (`json_object`, `json_group_array`) — тому власний JSON-парсер не потрібен.
3. **Власні SQL-функції.** Те, що SQL не вміє, додано в SQLite як функції на C:
   `sha256()`, `hash_password()`, `check_password()` (PBKDF2-HMAC-SHA256, 120 000 ітерацій),
   `slugify()` і `benchmark(n)` (хешує пароль у n потоках `pthread` — це дані для картки *Thread benchmark* на дашборді).
4. **Без спільного стану між потоками.** Кожен запит відкриває власне з'єднання з БД, тож потокам
   нічого не треба синхронізувати. Режим WAL дозволяє читанню не блокувати запис. Усі зміни в одному
   запиті виконуються в одній транзакції. Важке хешування паролів (`pre` у маршруті) виконується
   *до* транзакції, щоб не тримати блокування БД.

## REST API

Відповіді — JSON. Захищені маршрути вимагають заголовок `Authorization: Bearer <токен>`
(токен повертають `/api/register` і `/api/login`; діє 7 днів).

| Метод | Шлях | Доступ | Опис |
| --- | --- | --- | --- |
| GET | `/api/health` | всі | стан сервера |
| GET | `/api/posts?limit=&offset=` | всі | опубліковані пости (`{items,total}`) |
| GET | `/api/posts/:slug` | всі | один пост |
| GET | `/api/faqs` | всі | часті питання |
| POST | `/api/subscribe` | всі | підписка на розсилку `{email}` |
| POST | `/api/contact` | всі | повідомлення з форми `{name,email,message}` |
| POST | `/api/register` | всі | реєстрація `{name,email,password}` → `{token,user}` |
| POST | `/api/login` | всі | вхід `{email,password}` → `{token,user}` |
| GET | `/api/me` | користувач | поточний користувач |
| POST | `/api/logout` | користувач | відкликає токен |
| GET | `/api/admin/stats` | адмін | лічильники, графіки за 14 днів, стан сервера |
| GET | `/api/admin/benchmark?n=` | адмін | тест багатопотокового хешування (n = 1…16) |
| GET | `/api/admin/audit` | адмін | журнал подій |
| GET · PATCH · DELETE | `/api/admin/messages[/:id]` | адмін | повідомлення (`?unread=1`; `{is_read}`) |
| GET · DELETE | `/api/admin/subscribers[/:id]` | адмін | підписники |
| GET · PATCH · DELETE | `/api/admin/users[/:id]` | адмін | користувачі (`{role}`) |
| GET · POST · PUT · DELETE | `/api/admin/posts[/:id]` | адмін | керування постами |

Коди відповідей: 200/201 успіх · 400 битий JSON · 401 немає/поганий токен · 403 не адмін ·
404 не знайдено · 405 метод не підтримується · 409 email зайнятий · 413 запит завеликий · 422 не пройшла перевірка даних.

## База даних

SQLite, файл `database/nexcent.db` (створюється автоматично зі `schema.sql`; `seed.sql` застосовується один раз).
Сервер використовує таблиці `users`, `sessions`, `posts`, `faqs`, `messages`, `subscribers`, `audit_log`, `meta`.
Таблиці `workers` і `rate_limits` лишилися в `schema.sql` від попередньої версії сервера, але **більше не використовуються** —
їх можна видалити зі схеми, на роботу сервера це не впливає.

## Безпека (що є)

- Паролі: PBKDF2-HMAC-SHA256, випадкова сіль, порівняння за сталий час; у БД лише хеш.
- Токен сесії — 32 випадкових байти; у БД зберігається лише його SHA-256.
- Усі значення в SQL підставляються як параметри (`:body`, `:p`, ...) — SQL-ін'єкції неможливі.
- Статика: віддаються лише `index.html` і папки `pages/ css/ js/ images/`, шляхи з `..` відхиляються
  (`server/`, `database/` та інше закрито).
- Заголовки `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`.
- Тайм-аут читання 5 с, ліміт запиту 64 КБ, не більше ~200 одночасних з'єднань.

## Що спрощено порівняно з попередньою версією (4 726 рядків C у 22 файлах)

Прибрано: пул процесів `fork()` з наглядачем і heartbeat, пул потоків з чергою, обмеження частоти запитів
(rate limiting), власний JSON-парсер, парсер `.env`, CORS, `HEAD`, вирівнювання часу відповіді при вході
(захист від перебору email), докладні помилки по кожному полю (`fields`). Лишилося 26 тих самих ендпоінтів —
сайт (зокрема дашборд) працює без змін, а паролі й токени з бази старої версії лишаються чинними.
На дашборді блок *Server processes* тепер показує один процес.

## Обмеження

- Для навчального проєкту, не для production: немає HTTPS (потрібен reverse-proxy), немає rate limiting.
- Не тримайте проєкт у `/mnt/c` у WSL — SQLite у режимі WAL там працює ненадійно; кладіть у файлову систему Linux.
- Тіло запиту до 64 КБ (≈ 20 000 символів кирилиці в пості, якщо клієнт не екранує їх як `\uXXXX`).
- Перевірено на Linux із SQLite 3.45 і gcc; macOS/clang не перевірялись.

## Відповіді на типові питання на захисті

**Чому потоки, а не процеси?** Потоки легші: спільна пам'ять, дешеве створення. Тут вони майже не ділять стан
(кожен запит має власне з'єднання з БД), тому небезпечних гонок немає. Процеси дали б ізоляцію ціною складнішої
координації; для цього проєкту це зайве.

**Як уникаєте гонок?** Спільні лише лічильники `requests`/`active` (атомарні операції `__atomic_*`).
Усе інше — локальне для потоку. Конкурентні записи в БД серіалізує сам SQLite (транзакція `BEGIN IMMEDIATE`
+ `busy_timeout` 5 с); WAL дозволяє читачам працювати паралельно з записом.

**Чому хешування винесене з транзакції?** PBKDF2 займає ~70 мс CPU. Якщо рахувати його всередині транзакції запису,
усі інші записи чекали б. Тому `pre`-запит хешує до `BEGIN IMMEDIATE`.

**Навіщо PBKDF2 і сіль?** Повільний хеш ускладнює перебір паролів, а унікальна сіль робить однакові паролі різними
в БД та знешкоджує райдужні таблиці.

**Чому SQL у таблиці маршрутів?** Один рядок на ендпоінт: видно все — права, перевірку даних, зміну БД і форму
відповіді. SQLite вміє JSON, тож проміжний код «розібрати JSON → викликати SQL → зібрати JSON» не потрібен.

**Як працює benchmark?** `benchmark(n)` запускає n потоків `pthread`, кожен хешує пароль; порівнюється час із
послідовним виконанням. Прискорення залежить від кількості ядер CPU.

## Що перевірено

`make test` — 76 перевірок усіх маршрутів і статики. Окремо (поза репозиторієм): сервер під AddressSanitizer,
UBSan і ThreadSanitizer без зауважень; SHA-256 і PBKDF2 звірені з `hashlib` Python на 319 значеннях (межі блоків,
порожній і довгий паролі); однакові сценарії на старому і новому сервері дали ті самі HTTP-коди й структури JSON;
сайт пройшов наскрізний сценарій у Chromium (реєстрація, вхід, усі вкладки дашборду, створення/редагування/видалення поста).
